Flows that haunt whoever inherits them

Every tenant has one. A flow nobody remembers building, that nobody fully understands, and that nobody dares turn off because something, somewhere, might depend on it. It ran fine for months. Then one day it didn't, and the person who built it left two years ago.

None of these are bugs. They're design decisions that made perfect sense to the person who built the flow, and no sense at all to the person who inherits it. Here are five of the most common, and how to lay each one to rest.

1. The ghost owner

The flow belongs to someone who has left. It keeps running for a while, because their connections still work, until the account is disabled and every action that used their connection starts failing. Microsoft calls these orphaned flows: flows with no valid owner left.

How it gets in: the flow was built in someone's personal "My flows" area, with their own sign-in on every connection, and nobody else was ever added.

How to lay it to rest: add at least one co-owner to every flow that matters, and keep business-critical flows in solutions so ownership can be changed in place. For production, ask whether the flow should be owned by a service principal rather than a person: it can't leave, change its password or go on holiday. Admins can find orphaned flows in the Power Platform admin center, under the environment's Resources, by looking for flows with no owner listed.

2. The flow that wakes itself

A flow triggers when an item is modified. One of its actions updates that same item. The update counts as a modification, so the flow triggers again, and again, until someone notices the run history scrolling.

How it gets in: "When an item is modified" plus "Update item" on the same list, with nothing in between to tell the flow its own changes apart from a person's.

How to lay it to rest: add a trigger condition so the flow only starts when something meaningful has changed, for example a status column moving to a value the flow cares about. Or have the flow set a field that the trigger condition checks, so it ignores its own edits. The trigger condition builder writes the syntax for you.

3. The approval that never comes back

An approval is sent. The approver is on leave, or ignores it, or the email lands in a folder nobody reads. A cloud flow run can last at most 30 days, and that includes time spent waiting on an approval. On day 30 the pending step simply times out, and unless the flow handles that, nothing tells the requester.

How it gets in: an approval action with no expiry and no branch for "what if nobody answers".

How to lay it to rest: give every approval a sensible timeout and a branch configured to run when it has timed out: remind, escalate or close the request, but never leave it hanging. For processes that genuinely run longer than 30 days, split them into two flows, one that sends the approval and one that acts on the response, with the approval stored in Dataverse. The approval flow narration goes deeper on reminders and escalation.

4. The frozen clock

Someone puts utcNow() in a trigger's settings, perhaps to only pick up items created after "now". It looks right. But expressions in a trigger are worked out once, when the flow is saved, not each time it runs. "Now" is frozen at the moment of the last save, and the flow quietly behaves as if time stopped that day.

How it gets in: an expression that is dynamic everywhere else in a flow, used in the one place it isn't.

How to lay it to rest: keep time-based logic out of the trigger. Let the flow start, then check dates in a Condition or a Filter array step, where utcNow() is worked out on every run.

5. The flow that quietly falls asleep

The flow is still in the list and looks fine, but it's switched off, and nobody turned it off. Power Automate turns off a cloud flow whose trigger or actions fail continuously for 14 days. A flow that isn't triggered at all for 90 days may also be turned off unless its owner has a premium or capacity licence. Owners get a warning 30 days before that happens, which is no help when the owner has left. Connections can expire on their own too: a SharePoint connection that isn't used for 90 days stops working.

How it gets in: failures nobody sees, warnings sent to a mailbox nobody reads, and a flow that only runs once a quarter.

How to lay it to rest: add a failure notification to every flow that matters: a branch set to run only when an action has failed, sending the error to a shared mailbox or a Teams channel rather than one person. The flow error handler builds the pieces. Check run history on a schedule for production flows, and for anything that runs rarely, put a reminder in a shared calendar to check it still works before it's needed.

The exorcism checklist

If you inherit a flow this Halloween, five questions before you change anything:

  1. Who owns it, and are they still here?
  2. Can it trigger itself?
  3. What happens if nobody responds?
  4. Is there any expression in the trigger?
  5. Who finds out when it fails?

None of these take more than a few minutes to check. All of them are easier to answer now than at 4pm on a Friday when the flow has already stopped.
